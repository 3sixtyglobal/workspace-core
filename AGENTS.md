# AGENTS.md

Guidance for AI coding agents working in this repository. Human contributors should read [CONTRIBUTING](./CONTRIBUTING.md), which covers the same ground in more depth.

## Repository Overview

A pnpm monorepo of TypeScript packages.

- `packages/*` - Published libraries
- `apps/*` - Applications and command line tools, where present
- `docs` - Repository level documentation, including `packages.md`, `apps.md` where there are apps, and architecture articles where present
- `scripts` - Repository maintenance scripts used by the root `package.json` and the workflows

Each package follows the same layout: `src`, `tests`, `locales`, `docs` and its own `package.json`, `tsconfig.json` and `vitest.config.ts`. Within a package's `docs` folder:

- `examples.md` - Hand written usage examples, keep these in step with API changes
- `changelog.md` - Maintained by the release workflow, do not edit
- `reference` - Generated by `pnpm run docs`, do not edit or commit
- `open-api/spec.json` - Generated by `pnpm run docs:api` in REST service packages, do not edit by hand

## Setup

- Node.js, at the version given in the `engines` field of `package.json`
- pnpm, at the version pinned in the `packageManager` field of `package.json`
- Run `pnpm install`, never `npm install`, as there is no npm lockfile
- `pnpm install` also points git at the `.githooks` directory, which checks commit messages and branch names

## Commands

Run these from the repository root.

| Command                    | Purpose                                                        |
| -------------------------- | -------------------------------------------------------------- |
| `pnpm run format`          | Format everything with Prettier                                |
| `pnpm run lint`            | Formatting, ESLint, markdownlint and cspell checks             |
| `pnpm run dist`            | Clean, build, type check the tests and run them, per package   |
| `pnpm run dist:no-test`    | The same as `dist` without running the tests                   |
| `pnpm run quality`         | Format, lint, compile, validate locales and test, the CI gate  |
| `pnpm run quality:no-test` | The same as `quality` without the tests                        |
| `pnpm run test:coverage`   | Run the tests and write a coverage report per package          |
| `pnpm run lint:package`    | Check the packed package manifests with publint, after a build |

To work on a single package, run `pnpm run build`, `pnpm run test` or `pnpm run test:build` from its folder. To run a single spec file, or a single test within it, pass the path and an optional name filter from the package folder:

```shell
pnpm run test tests/utils/guards.spec.ts
pnpm run test tests/utils/guards.spec.ts -t "can fail with undefined"
```

Packages consume each other's built output, so build a dependency before testing a package that uses a changed API. Only `build`, `merge-locales`, `dist` and `dist:no-test` walk the packages in dependency order, the other root commands run across all packages at once.

To test against unreleased changes in a sibling repository, `pnpm run local-link <package-name>` links its local build into `node_modules`. Do not commit any changes this makes.

After linking or unlinking, delete the `.vitest-cache` folders outside `node_modules/.pnpm`, as Vitest keeps transforms of the linked build and checks such as `toThrow(GeneralError)` then fail. Undo a link with `pnpm run local-link <package-name> unlink`, as `pnpm install` does not. Search tools that respect `.gitignore` skip `node_modules`, so check what a published package contains with `npm pack <package>@<version> --dry-run`.

Always run `pnpm run format` before `pnpm run lint`. Work is not complete until `pnpm run quality` passes. If a command cannot be run, say which one and why. Never report an interrupted or timed out test run as passing.

## Code Conventions

The code conventions, including the rules for changing exported APIs, backwards compatibility and lint, are in [.claude/rules/code-conventions.md](./.claude/rules/code-conventions.md), read it before changing code in `src` or `tests`. ESLint enforces the rest, so `pnpm run lint` reports any that are broken.

## Licence Headers

Every source file starts with a licence header, one or more copyright lines followed by the SPDX line. The `header/header` lint rule enforces this.

New files use the default header, with the current year, even when copied or ported from a file with a different header:

```ts
// Copyright <year> 3Sixty Trade Ltd.
// SPDX-License-Identifier: Apache-2.0.
```

When you modify an existing file whose header has no `3Sixty Trade Ltd` copyright line, add one with the current year after the existing copyright lines and before the SPDX line. Keep the existing lines unchanged:

```ts
// Copyright <original year> <original holder>.
// Copyright <year> 3Sixty Trade Ltd.
// SPDX-License-Identifier: Apache-2.0.
```

If the file already has a `3Sixty Trade Ltd` line, leave it as it is.

## Localisation

User facing text, including error messages, comes from `locales/en.json` in each package. Error keys are nested under `error.<className>.<messageKey>`, where `<className>` is the class's `CLASS_NAME` in camel case. `pnpm run validate-locales` checks that every key used in the source exists and that no keys are unused.

## Tests

- Tests use Vitest with globals and live in `tests`, mirroring the `src` folder structure, as `*.spec.ts`
- Add or update tests alongside any behavioural change, and add tests where coverage is missing
- Shared test helpers live in `tests` alongside the specs, for example in a `helpers` folder or `setupTestEnv.ts`
- Test against third party infrastructure, such as databases or ledgers, using Docker images wherever possible. Add each service to `.github/workflows/setup-test-env/action.yaml` so CI starts it for the package's test run
- Packages that test against external services read their settings in `tests/setupTestEnv.ts` from `tests/.env` and the git ignored `tests/.env.dev`

## Documentation

- Write in UK English and do not use em dashes
- Keep `README.md` descriptions in step with the `description` field of `package.json`
- Markdown is checked by markdownlint and cspell; add genuine new words to `cspell.json` rather than rewording around them

## Change Rules

- Be brief in code, comments, documentation and commit messages
- Never use the term shapes, call them models, in code, comments and documentation
- Keep changes small and focused, without unrelated refactoring or formatting churn
- Do not modify configuration files unless asked, so they stay consistent across all the repositories. This covers `eslint.config.js`, `eslint.config-custom.js`, `prettier.config.mjs`, `commitlint.config.mjs`, the markdownlint files, `repo-structure.json`, `pnpm-workspace.yaml`, the `tsconfig*.json`, `vitest.config.ts` and `typedoc.config.mjs` files, and the `.github` workflows. The exceptions are adding words to `cspell.json` and adding test services to `setup-test-env`
- Pin every new dependency to an exact version, and avoid adding runtime dependencies where existing ones suffice. When you add one, explain why the existing ones are not enough
- Do not commit generated output such as `dist`, `coverage` or `docs/reference`, which is regenerated by a separate workflow
- Do not add a byte order mark to any file
- When adding a package, give its `package.json` the version its siblings have, and add it to both `release/release-please-config.*.json` files and to `release/release-please-manifest.prerelease.json` and `release/release-please-manifest.prod.json` with the versions its siblings have there. release-please reads the current version from the manifest, so a package missing from it is released as `0.0.1`. This is the one time a version is set by hand
- Before the first release of a new public package, publish a placeholder of it by hand, such as `0.20.0-next.0` with only a `README.md` and the `repository` field, so trusted publishing with OIDC can be enabled for it on npm, which the release workflow needs to publish it

## Git

Before creating a branch, committing or opening a pull request, read [Branch Management](./CONTRIBUTING.md#branch-management), [Commit Standards](./CONTRIBUTING.md#commit-standards) and [Pull Request Process](./CONTRIBUTING.md#pull-request-process) in CONTRIBUTING. The git hooks check branch names and commit messages. The pull request and issue templates are shared by every repository, from [3sixtyglobal/.github](https://github.com/3sixtyglobal/.github), so fill in the template when writing one.

- Do not commit or push unless asked
- Do not add AI attribution, such as "Generated with" lines or `Co-Authored-By` trailers, to commits, pull requests or issues
- Do not put email addresses anywhere in a commit, including the subject, body and trailers
- Do not bump versions or edit changelogs by hand, the release workflows produce them
